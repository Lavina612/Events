# Event Management API

Сервис для управления мероприятиями и системой их бронирования на платформе ASP.NET Core Web API с использованием **.NET 10**.
Сервис находится на шестом этапе разработки.

## 🚀 О проекте
Данное приложение представляет собой базовый REST API, реализующий полный цикл CRUD-операций для управления событиями, а также дополнительный функционал для создания бронирования событий. 
* **Архитектура**: Трёхслойная архитектура с тонкими контроллерами. Бизнес-логика изолирована в слое сервисов (`EventService`, `BookingService`), а работа с данными инкапсулирована в репозиториях (`EventRepository`, `BookingRepository`). Все зависимости скрыты за интерфейсами.
* **Хранение данных**: Полноценная реляционная база данных PostgreSQL. Взаимодействие с БД осуществляется через Entity Framework Core. Все сущности сопоставлены с таблицами, а правила валидации данных, связи и ограничения гибко настроены с помощью Fluent API в классах конфигураций. Схема данных полностью управляется миграциями EF Core. При старте приложения миграции применяются автоматически.
* **Валидация**: Автоматическая валидация входных данных на уровне модели DTO с использованием встроенных атрибутов и интерфейса `IValidatableObject`.
* **Фоновая обработка**: Асинхронная обработка заявок на бронирование с использованием встроенных фоновых служб (`BackgroundService`) подтверждает или отклоняет бронирование.

## 🛠️ Требования и настройка окружения
* **.NET 10 SDK** (или новее).
* **СУБД PostgreSQL** (рекомендуется запуск через Docker-контейнер с помощью `docker-compose.yml`).
* **Среда контейнеризации Docker** (Docker Desktop, Rancher Desktop или Colima) — необходима для запуска приложения локально и для выполнения интеграционных тестов.
* **Настроенная строка подключения** в секции `ConnectionStrings` в файле конфигурации `appsettings.json` (или `appsettings.Development.json`)
  Пример конфигурации для подключения к PostgreSQL в Docker:
  ```json
  "ConnectionStrings": {
      "Default": "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=postgres"
  }
  ```

## 📦 Управление миграциями базы данных (EF Core)

База данных инициализируется и обновляется с помощью механизма миграций Entity Framework Core. При запуске приложения миграции применяются автоматически, разворачивая актуальную схему.

При внесении изменений в модели данных или конфигурации Fluent API, необходимо обновить миграции. Для этого, находясь в папке проекта `EventsRestApi`, используйте следующие команды:

* **Не забудьте установить утилиту `dotnet ef` для работы с миграциями, если она ещё не установлена:**
  ```bash
  dotnet tool install --global dotnet-ef
  ```

* **Создание новой миграции:**
  ```bash
  dotnet ef migrations add <Название_Миграции>
  ```
  
* **Ручное применение миграций на локальную БД:**
  ```bash
  dotnet ef database update
  ```
  
* **Удаление последней (еще не примененной) миграции:**
  ```bash
  dotnet ef migrations remove
  ```

#### Спецификация эндпоинтов (REST)

| Метод | Эндпоинт | Описание | Успешный статус | Ошибки |
| :--- | :--- | :--- | :--- | :--- |
| **GET** | `/events` | Получить список всех мероприятий | `200 OK` | — |
| **GET** | `/events/{id}` | Получить мероприятие по его `id` | `200 OK` | `404 Not Found` |

| **PUT** | `/events/{id}` | Обновить существующее мероприятие по его `id` | `204 NoContent` | `400 BadRequest` (валидация), `404 Not Found` |

| **POST** | `/events/{eventId}/book` | Создать бронирование на мероприятие | `202 Accepted` | `404 Not Found` (событие не найдено), `409 Conflict` (нет доступных мест), `422 UnprocessableEntity` (событие уже завершилось) |
| **GET** | `/bookings/{id}` | Получить текущее состояние бронирования по его `id` | `200 OK` | `404 Not Found` |

#### 🔍 Параметры фильтрации и пагинации (GET /events)

При получении списка всех мероприятий вы можете использовать следующие опциональные `query`-параметры в строке запроса:

| Параметр | Тип | Описание | Пример |
| :--- | :--- | :--- | :--- |
| `title` | `string` | Частичный поиск по названию (регистронезависимый) | `/events?title=stand-up` |
| `from` | `DateTime` | Фильтр даты начала (включая указанную дату и позже) | `/events?from=2026-06-01` |
| `to` | `DateTime` | Фильтр даты окончания (включая указанную дату и раньше) | `/events?to=2026-06-30` |
| `page` | `int` | Номер запрашиваемой страницы (по умолчанию: `1`) | `/events?page=2` |
| `pageSize` | `int` | Количество элементов на странице (по умолчанию: `10`) | `/events?pageSize=5` |

При успешном запросе с пагинацией сервер возвращает статус `200 OK` и JSON-объект следующей структуры:
```json
{
  "itemsForPage": [ /* массив подходящих мероприятий */ ],
  "totalCount": 5,
  "page": 2,
  "pageSize": 2,
  "totalPages": 3
}
```

### ⚠️ Правила валидации данных (DTO)

При отправке запросов `POST` и `PUT` данные автоматически проверяются по следующим критериям:
1. Название события (`Title`) обязательно для заполнения и не может быть пустым.
2. Даты начала (`StartAt`) и окончания (`EndAt`) мероприятия обязательны для заполнения.
3. Дата окончания мероприятия (`EndAt`) должна быть позже даты начала (`StartAt`).
4. Общее количество мест на мероприятии (`TotalSeats`) обязательно для заполнения и должно быть положительным числом.

#### Пример данных в формате JSON, которые должны быть переданы в теле запроса для создания мероприятия (`POST /events`):
```json
{
  "title": "Мероприятие 1",
  "description": "Описание 1",
  "startAt": "2026-05-10T10:00:00Z",
  "endAt": "2026-05-15T12:00:00Z",
  "totalSeats": 10
}
```
*(Обратите внимание: `id` при создании передавать не нужно, сервер сгенерирует его автоматически)*.

#### Пример данных в формате JSON, которые должны быть переданы в теле запроса при обновлении мероприятия (`PUT /events/{id}`):
```json
{
  "title": "Мероприятие 1",
  "description": "Описание 1",
  "startAt": "2026-05-10T10:00:00Z",
  "endAt": "2026-05-15T12:00:00Z",
  "totalSeats": 10
}
```

### 🛑 Формат ответа при ошибках

В проекте настроена стандартизированная обработка ошибок (через глобальный Middleware). При возникновении непредвиденных исключений сервер возвращает ответ в общепринятом формате **Problem Details** (согласно спецификации RFC 7807):

#### 1. Ошибка валидации данных (400 Bad Request)
Возвращается при нарушении правил валидации DTO.

#### 2. Ресурс не найден (404 Not Found)
Возвращается при отсутствии запрашиваемого ресурса в системе.

#### 3. Конфликт бизнес-логики: отсутствие свободных мест на мероприятие (409 Conflict)
Возвращается при отсутствии доступных мест на мероприятии для бронирования.

#### 4. Необрабатываемая сущность (422 Unprocessable Entity)
Возвращается при попытке создать бронирование, которое нарушает бизнес-логику (например, при попытке забронировать места на завершившееся мероприятие).

#### 5. Внутренняя ошибка сервера (500 Internal Server Error)
Возвращается при любых непредвиденных технических сбоях в коде приложения. Ошибка логируется на сервере, а клиент получает безопасное стандартизированное сообщение.

### ⚙️ Фоновая обработка бронирований

В приложении развернут фоновый сервис `BookingBackgroundService`, обрабатывающий бронирования пачками по 5 штук (размер пачки настраивается в конфигурации приложения):
*   **Параллельная обработка**: Сервис периодически запрашивает из хранилища пачку необработанных бронирований (статус: `Pending`), запускает их обработку одновременно и дожидается окончания обработки всех бронирований из пачки.
*   **Обращение к внешней системе**: Для каждого бронирования имитируется обращение к внешней системе с помощью временной задержки (`Task.Delay`).
*   **Разветвление бизнес-логики**: По завершении обработки бронирования ему обновляется статус (`Status`) и время обработки (`ProcessedAt`), а затем оно сохраняется в системе. Возможные статусы:
    *   `Confirmed` (Подтверждено): Если мероприятие не удалено из системы и ещё не завершилось.
    *   `Rejected` (Отклонено): Если мероприятие удалено из системы или завершилось. Если событие уже завершилось, забронированные места мероприятия становятся доступными (`ReleaseSeats`). В случае возникновения любых непредвиденных технических сбоев бронирование также переводится в статус `Rejected` ради безопасности данных.
*   **Оптимизация ресурсов**: Если фоновый сервис обработал полную пачку задач, он мгновенно запрашивает следующую для обработки. Если пачка оказалась неполной, сервис переходит в небольшое ожидание, после чего повторяет попытку получения задач.

### 🔒 Синхронизация потоков и консистентность данных

#### Использование примитивов синхронизации
Поскольку веб-сервер обрабатывает HTTP-запросы конкурентно в разных потоках, а также параллельно работает фоновый сервис обработки заявок (`ProcessPendingBookingsBunchAsync`), возникает потенциальное состояния гонки (**Race Condition**), которое может привести к нарушению целостности данных.

Для предотвращения этой проблемы внутри `BookingService` и `BookingBackgroundService` используется `SemaphoreSlim(1, 1)`, который защищает критические секции кода при создании нового бронирования (`BookingService/CreateBookingAsync`), и при фоновой обработке заявок (`BookingBackgroundService/ProcessBookingAsync`), позволяя **только одному потоку в один момент времени** как-либо работать с конкретным бронированием. Все остальные потоки в это время асинхронно ожидают своей очереди, не блокируя потоки операционной системы.

#### Пример сценария с овербукингом
**Исходные данные:**
*   Создано мероприятие с `TotalSeats = 1` и `AvailableSeats = 1`.

**Пошаговый сценарий при параллельных запросах:**
1. **Пользователь А** отправляет запрос `POST /events/{id}/book?requestedSeats=1`.
2. **Пользователь Б** одновременно отправляет точно такой же запрос `POST /events/{id}/book?requestedSeats=1`.
3. Поток **Пользователя А** выполняет логику:
   * Находит событие (`AvailableSeats = 1`).
   * Вызывает `TryReserveSeats(1)`. Мест хватает, и он готовится записать новое значение `AvailableSeats = 0`
4. Но в этот момент поток **Пользователя Б** вклинивается в работу и тоже:
   * Находит событие (всё ещё `AvailableSeats = 1`).
   * Вызывает `TryReserveSeats(1)`. Мест хватает, и он записывает новое значение `AvailableSeats = 0`
5. Поток **Пользователя А** продолжает выполнение:
   * Записывает новое значение `AvailableSeats = 0`, хотя на самом деле по логике уже должен записать `AvailableSeats = -1`.
6. **Произошел овербукинг!**

**Решение:**

За счёт корректного использования правильных примитивов синхронизации в приложении сценарий овербукинга невозможен, данные защищены!

## 🧪 Запуск автоматических тестов (xUnit)

В репозитории реализовано два типа автоматических тестов:

### 1. Юнит-тесты (Unit Tests)
Проверяют изолированную бизнес-логику: правильность работы CRUD-операций в сервисе событий, а также сценарии создания бронирований, их получения, и изменения статуса бронирования фоновым сервисом. 

* Для обеспечения скорости выполнения  тестов реальная база данных в них не используется — вместо этого в тестовых классах регистрируется провайдер InMemory базы данных (`options.UseInMemoryDatabase`), генерирующий уникальную чистую БД для каждого тестового прогона.

### 2. Интеграционные тесты (Integration Tests)

Проверяют корректность работы слоя данных (репозиториев) и компонентов со сложной SQL-трансляцией в реальных условиях взаимодействия с СУБД.

* Тесты используют библиотеку Testcontainers для автоматического разворачивания полноценной изолированной базы данных в контейнере `postgres:16-alpine`.

* Перед стартом каждого тестового класса Testcontainers поднимает чистый контейнер, накатывает на него все актуальные миграции EF Core, а после завершения тестов полностью уничтожает окружение.

* Чтобы тесты не влияли друг на друга и оставались детерминированными, перед выполнением каждого отдельного тест-кейса таблицы полностью очищаются с помощью команды `TRUNCATE ... RESTART IDENTITY CASCADE` (реализовано в методе ResetDatabaseAsync). Это гарантирует, что каждый тест запускается на абсолютно чистой базе данных.

* Помимо репозиториев, интеграционные тесты также проверяют работу метода получения страницы мероприятий `GetPageAsync` из `EventService`. Это сделанно из-за того, что репозиторий возвращает сырой IQueryable<Event>, а в самом сервисе используются специфичные для PostgreSQL конструкции (такие как `EF.Functions.ILike`). Тестирование этого метода на InMemory провайдере невозможно — корректно проверить трансляцию этого LINQ-выражения в SQL и работу пагинации с фильтрацией можно только на реальной СУБД.

⚠️ **Важно:** Для успешного выполнения интеграционных тестов должен быть запущен Docker-демон.

  ```bash
  dotnet test
  ```
