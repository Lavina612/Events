# Event Management API

Сервис для управления мероприятиями и системой их бронирования на платформе ASP.NET Core Web API с использованием **.NET 10**.
Сервис находится на восьмом этапе разработки.

## 🚀 О проекте
Данное приложение представляет собой базовый REST API, реализующий полный цикл CRUD-операций для управления событиями, а также дополнительный функционал для создания бронирования событий. 
* **Архитектура**: Приложение спроектировано с использованием принципов Clean Architecture (Чистой архитектуры) и разделено на независимые изолированные слои:
  * `EventsRestApi.Domain` — ядро приложения. Содержит бизнес-сущности (`Models`), доменную логику и кастомные исключения доменного уровня. Не имеет внешних зависимостей от других слоев или фреймворков.
  * `EventsRestApi.Application` — слой бизнес-логики. Реализует основные сценарии использования системы посредством сервисов (`Services`), содержит контракты репозиториев (`RepositoryInterfaces`), объекты передачи данных (`Dto`), мапперы для преобразования доменных сущностей в DTO и обратно (`Mappers`), классы конфигурации (`Settings`), кастомные исключения прикладного уровня (`Exceptions`) и `DependencyInjection.cs` для централизованной регистрации всех сервисов и компонентов прикладного слоя в DI-контейнере.
  * `EventsRestApi.Infrastructure` — слой реализации инфраструктуры. Отвечает за доступ к данным (Entity Framework Core `DbContext`, конфигурации Fluent API, `Repositories`), управление миграциями базы данных и регистрацию внешних зависимостей, а также содержит `DependencyInjection.cs` для централизованной регистрации всех внешних зависимостей инфраструктурного слоя в DI-контейнере.
  * `EventsRestApi.Presentation` — точка входа и слой представления (ASP.NET Core Web API). Содержит контроллеры (`Controllers`), кастомные `Middlewares` для глобальной обработки ошибок, файлы конфигурации (`appsettings.json`) и класс `Program.cs`.
* **Хранение данных**: Полноценная реляционная база данных PostgreSQL. Взаимодействие с БД осуществляется через Entity Framework Core. Все сущности сопоставлены с таблицами, а правила валидации данных, связи и ограничения гибко настроены с помощью Fluent API в классах конфигураций. Схема данных полностью управляется миграциями EF Core. При старте приложения миграции применяются автоматически.
* **Валидация**: Автоматическая валидация входных данных на уровне модели DTO с использованием встроенных атрибутов и интерфейса `IValidatableObject`.
* **Фоновая обработка**: Асинхронная обработка заявок на бронирование с использованием встроенных фоновых служб (`BackgroundService`) подтверждает или отклоняет бронирование.

## 📦 Миграциями базы данных (EF Core)

База данных инициализируется и обновляется с помощью механизма миграций Entity Framework Core. При запуске приложения миграции применяются автоматически, разворачивая актуальную схему.

### 🗺️ Управление миграциями

При внесении изменений в модели данных или конфигурации Fluent API, необходимо обновить миграции. Поскольку проект разделен на слои, при выполнении команд необходимо явно указывать стартовый проект (`Presentation`) и целевой проект с контекстом БД (`Infrastructure`).

Для управления миграциями, находясь в корневой папке решения (`EventsRestApi`), используйте следующие команды:

* **Установка утилиты `dotnet ef` (если ещё не установлена):**
  ```bash
  dotnet tool install --global dotnet-ef
  ```

* **Создание новой миграции:**
  ```bash
  dotnet ef migrations add <Название_Миграции> --project EventsRestApi.Infrastructure --startup-project EventsRestApi.Presentation
  ```
  
* **Ручное применение миграций на локальную БД:**
  ```bash
  dotnet ef database update --project EventsRestApi.Infrastructure --startup-project EventsRestApi.Presentation
  ```
  
* **Удаление последней (еще не примененной) миграции:**
  ```bash
  dotnet ef migrations remove --project EventsRestApi.Infrastructure --startup-project EventsRestApi.Presentation
  ```

### 📊 Миграции в проекте

#### 1. InitialCreate

Формирует базовую структуру базы данных в соответствии с конфигурациями Fluent API. Схема использует стратегию именования `snake_case` (все таблицы, колонки и ограничения пишутся строчными буквами через подчеркивание).

Миграция создает две основные таблицы, связи и встроенные проверки данных на уровне СУБД:

#### 1) Таблица `events` (Мероприятия)
* `id` (`uuid`, Primary Key) — уникальный идентификатор мероприятия (генерируется на стороне приложения).
* `title` (`varchar(250)`, Not Null) — название мероприятия с ограничением до 250 символов.
* `description` (`varchar(2000)`, Nullable) — описание мероприятия с ограничением до 2000 символов.
* `start_at` (`timestamp with time zone`, Not Null) — дата и время начала  мероприятия (связано с приватным полем `_startAt`).
* `end_at` (`timestamp with time zone`, Not Null) — дата и время окончания мероприятия (связано с приватным полем `_endAt`).
* `total_seats` (`integer`, Not Null) — общее количество мест на мероприятии (связано с приватным полем `_totalSeats`).
* `available_seats` (`integer`, Not Null) — количество оставшихся свободных мест (связано с приватным полем `_availableSeats`).

**🔒 Проверки целостности (Check Constraints):**
* `CK_Event_Dates`: Дата начала должна быть строго меньше даты окончания (`start_at < end_at`).
* `CK_Event_TotalSeats`: Общее количество мест должно быть положительным числом (`total_seats > 0`).
* `CK_Event_AvailableSeats`: Количество свободных мест не может быть отрицательным и не может превышать общее количество мест на мероприятии (`available_seats >= 0 AND available_seats <= total_seats`).

#### 2) Таблица `bookings` (Бронирования)
* `id` (`uuid`, Primary Key) — уникальный идентификатор брони (генерируется на стороне приложения).
* `event_id` (`uuid`, Not Null) — внешний ключ, связывающий бронирование с мероприятием.
* `status` (`varchar`, Not Null) — текущий статус обработки, сохраняемый в виде строки (`Pending`, `Confirmed`, `Rejected`).
* `booked_seats` (`integer`, Not Null) — количество забронированных мест.
* `created_at` (`timestamp with time zone`, Not Null) — дата и время создания заявки.
* `processed_at` (`timestamp with time zone`, Nullable) — дата и время обработки заявки фоновым сервисом.

**🔒 Проверки целостности (Check Constraints):**
* `CK_Booking_BookedSeats`: Количество бронируемых мест должно быть больше нуля (`booked_seats > 0`).
* `CK_Booking_Dates`: Заявка не может быть обработана раньше, чем она была создана (`processed_at IS NULL OR created_at <= processed_at`).

#### 🔗 Ограничения и связи (Constraints)
* **Foreign Key (`fk_bookings_events_event_id`):** Настроена связь «один ко многим» между таблицами `events` и `bookings`. Каждое мероприятие может содержать коллекцию связанных бронирований. При удалении мероприятия из базы данных автоматически срабатывает каскадное удаление (`ON DELETE CASCADE`) всех связанных с ним записей бронирования.

#### 2. AddUserTable

Добавляет новую таблицу `users` и связывает её с бронированиями. 

#### 1) Таблица `users` (Пользователи) — *Новая таблица*
* `id` (`uuid`, Primary Key) — уникальный идентификатор пользователя.
* `login` (`text`, Not Null) — логин пользователя для авторизации.
* `hashed_password` (`text`, Not Null) — хэшированный пароль.
* `role` (`text`, Not Null) — роль пользователя в системе.

**⚡ Индексы:**
* `ix_users_login`: Уникальный индекс (`unique: true`) на колонку `login` для предотвращения регистрации дубликатов.

#### 2) Изменения в таблице `bookings` (Бронирования)
* `user_id` (`uuid`, Not Null) — *Новая колонка*. Внешний ключ для связи бронирования с создавшим его пользователем. 

**⚡ Индексы:**
* `ix_bookings_user_id`: Индекс на новую колонку `user_id` для оптимизации запросов выборки броней конкретного пользователя.

#### 🔗 Ограничения и связи (Constraints)
* **Foreign Key (`fk_bookings_users_user_id`):** Настроена связь «один ко многим» между таблицами `users` и `bookings`. Каждому пользователю может принадлежать несколько бронирований. При удалении аккаунта пользователя из базы данных автоматически срабатывает каскадное удаление (`ON DELETE CASCADE`) всех связанных с ним записей бронирований.

### 🔒 Аутентификация и Авторизация

В проекте реализована полноценная система аутентификации и авторизации пользователей на основе **JWT (JSON Web Tokens)** и хэширования паролей с помощью алгоритма SHA-256.

#### 🛠️ Настройка конфигурации (appsettings.json)

Для корректной работы системы авторизации и запуска приложения необходимо заполнить секцию `JwtSettings` в файле конфигурации `appsettings.json`.

Пример структуры файла:

```json
{
  "JwtSettings": {
    "Issuer": "EventsRestApi.Backend",
    "Audience": "EventsRestApi.Clients",
    "Secret": "Здесь_должна_быть_ваша_длинная_секретная_строка_минимум_256_бит",
    "LifetimeInMinutes": 60
  }
}
```

> ⚠️ **Важно:** Секретный ключ (`Secret`) должен быть достаточно длинным для обеспечения безопасности подписи алгоритма HMAC-SHA256. В реальных production-средах никогда не храните реальные секреты в `appsettings.json`, используйте Environment Variables или секрет-менеджеры (например, User Secrets для локальной разработки).

#### 🎫 Механизм работы JWT

1. **Генерация токена:** При успешном вызове `/user/login` сервис генерирует токен, в который зашиваются утверждения (Claims) о пользователе:
   * Идентификатор пользователя (`nameid` / `NameIdentifier`)
   * Логин (`unique_name` / `Name`)
   * Роль (`role` / `Role`), определяющая уровень прав доступа к эндпоинтам (например, `Admin`, `User`).
2. **Валидация:** При получении запроса API строго сверяет издателя (`Issuer`), аудиторию (`Audience`), проверяет срок действия токена (`Lifetime`) с учетом нулевого временного сдвига (`ClockSkew = TimeSpan.Zero`), а также контролирует валидность подписи ключа (`Secret`).

#### 👥 Ролевая модель (Матрица доступа)
Доступ к эндпоинтам системы разграничен на три уровня в зависимости от статуса аутентификации и роли пользователя:

* **🌐 `Гость` (Неавторизованный пользователь):**
  * Может просматривать полный список доступных мероприятий с использованием фильтров и пагинации.
  * Может просматривать информацию о конкретном событии по его идентификатору.
* **🔑 `User` (Авторизованный пользователь):**
  * Обладает всеми возможностями `Гостя`.
  * Может создавать заявки на бронирование мероприятия.
  * Может просматривать список с информацией о всех своих бронированиях.
  * Может отменять свои бронирования.
* **🔐 `Admin` (Администратор):**
  * Обладает всеми возможностями `User`.
  * Может управлять мероприятиями: создание, изменение и удаление события.
  * Может просматривать учетные данные зарегистрированных пользователей по их `id`.
  * Может отменять любые бронирования.

#### 🔑 Хэширование паролей

В целях безопасности пароли пользователей не хранятся в открытом виде. При регистрации пароль переводится в верхний регистр Hex-строки хэша **SHA-256** силами `PasswordService`. Валидация при входе происходит путем сравнения хэша заново введенного пароля с хэшем из базы данных.

#### 📝 Тестирование защищенных запросов в Swagger

В проект встроена поддержка авторизации через интерфейс Swagger UI. 

Для вызова эндпоинтов, требующих авторизации (`[Authorize]`):
1. Выполните POST-запрос на эндпоинт `/user/login`, передав валидные креды.
2. Скопируйте строку полученного токена из ответа (`TokenResponseDto`).
3. В самом верху страницы Swagger нажмите кнопку **Authorize**.
4. В открывшемся окне введите только ваш скопированный JWT-токен (префикс `Bearer` добавлять не нужно, Swagger подставит его автоматически).
5. Нажмите **Authorize**, закройте окно и отправляйте запросы к защищенным эндпоинтам.

### Спецификация эндпоинтов (REST)

Все эндпоинты разделены по контроллерам в соответствии с их логическими обязанностями. Авторизация в системе реализуется с помощью JWT-токенов.

#### 📅 Events API (`EventsController`)
*Управление мероприятиями и создание бронирования на конкретное мероприятие.*

| Метод | Эндпоинт | Доступ | Описание и параметры | Успех | Ошибки |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **GET** | `/events` | 🌐 Гость | Получить список мероприятий с фильтрацией и пагинацией.<br>Параметры (Query): `title`, `from`, `to`, `page` (по умолч: 1), `pageSize` (по умолч: 10, макс: 100) | `200 OK` | `500` |
| **GET** | `/events/{id}` | 🌐 Гость | Получить информацию о мероприятии по его `id` | `200 OK` | `404`, `500` |
| **POST** | `/events` | 🔐 Admin | Создать новое мероприятие.<br>Параметры (Body): `EventRequestDto` | `201 Created` | `401`, `403`, `500` |
| **PUT** | `/events/{id}` | 🔐 Admin | Обновить данные существующего мероприятия по его `id` | `204 NoContent` | `400`, `401`, `403`, `404`, `500` |
| **DELETE**| `/events/{id}` | 🔐 Admin | Удалить мероприятие по его `id` | `204 NoContent` | `401`, `403`, `404`, `500` |
| **POST** | `/events/{eventId}/book` | 🔑 User / Admin | Создать бронирование на мероприятие.<br>Параметры (Query): `requestedSeats` (мин: 1) | `202 Accepted` | `400`, `401`, `404`, `409`, `500` |

#### 🎟️ Bookings API (`BookingsController`)
*Просмотр и управление бронированиями авторизованного пользователя.*

| Метод | Эндпоинт | Доступ | Описание и параметры | Успех | Ошибки |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **GET** | `/bookings` | 🔑 User / Admin | Получить список всех бронирований текущего авторизованного пользователя | `200 OK` | `401`, `500` |
| **GET** | `/bookings/{id}` | 🔑 User / Admin | Получить информацию о бронировании по его `id` | `200 OK` | `401`, `403`, `404`, `500` |
| **POST** | `/bookings/{id}/cancel` | 🔑 User (только свою бронь) / Admin | Отменить бронирование по его `id` | `204 NoContent` | `400`, `401`, `403`, `404`, `500` |

#### 👤 User API (`UserController`)
*Регистрация, аутентификация и администрирование пользователей.*

| Метод | Эндпоинт | Доступ | Описание и параметры | Успех | Ошибки |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **POST** | `/user/register` | 🌐 Гость | Регистрация нового пользователя.<br>Параметры (Body): `UserCredentialsDto`, (Query): `role` (по умолч: `User`) | `201 Created` | `400`, `409`, `500` |
| **POST** | `/user/login` | 🌐 Гость | Аутентификация пользователя и выдача JWT-токена.<br>Параметры (Body): `UserCredentialsDto` | `200 OK` | `400`, `401`, `500` |
| **GET** | `/user/{id}` | 🔐 Admin | Получить профиль пользователя по его `id` | `200 OK` | `401`, `403`, `404`, `500` |

#### 🔍 Параметры фильтрации и пагинации (GET /events)

При получении списка всех мероприятий вы можете использовать следующие опциональные `query`-параметры в строке запроса:

| Параметр | Тип | Описание | Пример |
| :--- | :--- | :--- | :--- |
| `title` | `string` | Частичный поиск по названию (регистронезависимый) | `/events?title=stand-up` |
| `from` | `DateTime` | Фильтр даты начала (включая указанную дату и позже) | `/events?from=2026-06-01` |
| `to` | `DateTime` | Фильтр даты окончания (включая указанную дату и раньше) | `/events?to=2026-06-30` |
| `page` | `int` | Номер запрашиваемой страницы (по умолчанию: `1`) | `/events?page=2` |
| `pageSize` | `int` | Количество элементов на странице (по умолчанию: `10`, максимальное: 100) | `/events?pageSize=5` |

При успешном запросе с пагинацией сервер возвращает статус `200 OK` и JSON-объект следующей структуры:
```json
{
  "itemsForPage": [ /* массив подходящих мероприятий */ ],
  "totalCount": 5,
  "page": 2,
  "pageSize": 2,
  "totalPages": 3
}
```

### ⚠️ Правила валидации данных (DTO)

При отправке запросов `POST` и `PUT` данные автоматически проверяются по следующим критериям:
1. Название события (`Title`) обязательно для заполнения и не может быть пустым.
2. Даты начала (`StartAt`) и окончания (`EndAt`) мероприятия обязательны для заполнения.
3. Дата окончания мероприятия (`EndAt`) должна быть позже даты начала (`StartAt`).
4. Общее количество мест на мероприятии (`TotalSeats`) обязательно для заполнения и должно быть положительным числом.

#### Пример данных в формате JSON, которые должны быть переданы в теле запроса для создания мероприятия (`POST /events`):
```json
{
  "title": "Мероприятие 1",
  "description": "Описание 1",
  "startAt": "2026-05-10T10:00:00Z",
  "endAt": "2026-05-15T12:00:00Z",
  "totalSeats": 10
}
```
*(Обратите внимание: `id` при создании передавать не нужно, сервер сгенерирует его автоматически)*.

#### Пример данных в формате JSON, которые должны быть переданы в теле запроса при обновлении мероприятия (`PUT /events/{id}`):
```json
{
  "title": "Мероприятие 1",
  "description": "Описание 1",
  "startAt": "2026-05-10T10:00:00Z",
  "endAt": "2026-05-15T12:00:00Z",
  "totalSeats": 10
}
```

### 🛑 Формат ответа при ошибках

В проекте настроена стандартизированная обработка ошибок через глобальный Middleware (`GlobalExceptionHandlingMiddleware`). При возникновении непредвиденных исключений сервер возвращает ответ в общепринятом формате **Problem Details** (согласно спецификации RFC 7807):

#### 1. Некорректный запрос (400 Bad Request)
* Нарушение правил валидации DTO.
* Передача некорректных параметров (`ArgumentException` + `paramName`).
* Попытка взаимодействия с уже завершившимся мероприятием (`FinishedEventException` + `eventId`, `endAt`).
* Попытка создать бронирование на мероприятие, которое уже началось (`StartedEventException` + `eventId`, `startAt`).

#### 2. Ошибки аутентификации (401 Unauthorized)
* Неверный логин или пароль при авторизации (`InvalidCredentialsException`).
* Некорректный, просроченный или поврежденный JWT-токен (`InvalidTokenException` + `claimName`).

#### 3. Ошибка авторизации (403 Forbidden)
* У пользователя недостаточно прав для выполнения данной операции (`ForbiddenException` + `userId`).

#### 4. Ресурс не найден (404 Not Found)
* Запрашиваемый ресурс (мероприятие, бронирование или пользователь) не найден в системе (`BaseNotFoundException` + `Id, `resourceType`).

#### 5. Конфликты бизнес-логики (409 Conflict)
* На мероприятии не осталось достаточного количества свободных мест (`NoAvailableSeatsException` + `eventId`, `requestedSeats`, `availableSeats`).
* Пользователь превысил допустимый лимит активных бронирований (`ExceedingActiveBookingLimitException` + `userId`, `bookingLimit`).
* Попытка регистрации пользователя с логином, который уже занят (`UserAlreadyExistsException` + `login`).

#### 6. Внутренняя ошибка сервера (500 Internal Server Error)
* Возвращается при любых непредвиденных технических сбоях в коде приложения. Ошибка логируется на сервере для последующего анализа разработчиками, а клиент получает безопасное стандартизированное сообщение без деталей реализации.

### ⚙️ Фоновая обработка бронирований

В приложении развернут фоновый сервис `BookingBackgroundService`, обрабатывающий бронирования пачками по 5 штук (размер пачки настраивается в конфигурации приложения):
*   **Параллельная обработка**: Сервис периодически запрашивает из хранилища пачку необработанных бронирований (статус: `Pending`), запускает их обработку одновременно и дожидается окончания обработки всех бронирований из пачки.
*   **Обращение к внешней системе**: Для каждого бронирования имитируется обращение к внешней системе с помощью временной задержки (`Task.Delay`).
*   **Разветвление бизнес-логики**: По завершении обработки бронирования ему обновляется статус (`Status`) и время обработки (`ProcessedAt`), а затем оно сохраняется в системе. Возможные статусы:
    *   `Confirmed` (Подтверждено): Если мероприятие не удалено из системы и ещё не завершилось.
    *   `Rejected` (Отклонено): Если мероприятие удалено из системы или завершилось. Если событие уже завершилось, забронированные места мероприятия становятся доступными (`ReleaseSeats`). В случае возникновения любых непредвиденных технических сбоев бронирование также переводится в статус `Rejected` ради безопасности данных.
*   **Оптимизация ресурсов**: Если фоновый сервис обработал полную пачку задач, он мгновенно запрашивает следующую для обработки. Если пачка оказалась неполной, сервис переходит в небольшое ожидание, после чего повторяет попытку получения задач.

### 🔒 Синхронизация потоков и консистентность данных

#### Использование примитивов синхронизации
Поскольку веб-сервер обрабатывает HTTP-запросы конкурентно в разных потоках, а также параллельно работает фоновый сервис обработки заявок (`ProcessPendingBookingsBunchAsync`), возникает потенциальное состояния гонки (**Race Condition**), которое может привести к нарушению целостности данных.

Для предотвращения этой проблемы внутри `BookingService` и `BookingBackgroundService` используется `SemaphoreSlim(1, 1)`, который защищает критические секции кода при создании нового бронирования (`BookingService/CreateBookingAsync`), и при фоновой обработке заявок (`BookingBackgroundService/ProcessBookingAsync`), позволяя **только одному потоку в один момент времени** как-либо работать с конкретным бронированием. Все остальные потоки в это время асинхронно ожидают своей очереди, не блокируя потоки операционной системы.

#### Пример сценария с овербукингом
**Исходные данные:**
*   Создано мероприятие с `TotalSeats = 1` и `AvailableSeats = 1`.

**Пошаговый сценарий при параллельных запросах:**
1. **Пользователь А** отправляет запрос `POST /events/{id}/book?requestedSeats=1`.
2. **Пользователь Б** одновременно отправляет точно такой же запрос `POST /events/{id}/book?requestedSeats=1`.
3. Поток **Пользователя А** выполняет логику:
   * Находит событие (`AvailableSeats = 1`).
   * Вызывает `TryReserveSeats(1)`. Мест хватает, и он готовится записать новое значение `AvailableSeats = 0`
4. Но в этот момент поток **Пользователя Б** вклинивается в работу и тоже:
   * Находит событие (всё ещё `AvailableSeats = 1`).
   * Вызывает `TryReserveSeats(1)`. Мест хватает, и он записывает новое значение `AvailableSeats = 0`
5. Поток **Пользователя А** продолжает выполнение:
   * Записывает новое значение `AvailableSeats = 0`, хотя на самом деле по логике уже должен записать `AvailableSeats = -1`.
6. **Произошел овербукинг!**

**Решение:**

За счёт корректного использования правильных примитивов синхронизации в приложении сценарий овербукинга невозможен, данные защищены!

## 🧪 Запуск автоматических тестов (xUnit)

В репозитории реализовано два типа автоматических тестов:

### 1. Юнит-тесты (Unit Tests)
Проверяют изолированную бизнес-логику: правильность работы CRUD-операций в сервисе событий, а также сценарии создания бронирований, их получения, и изменения статуса бронирования фоновым сервисом. 

* Для обеспечения скорости выполнения тестов реальная база данных в них не используется — вместо этого в тестовых классах регистрируется провайдер InMemory базы данных (`options.UseInMemoryDatabase`), генерирующий уникальную чистую БД для каждого тестового прогона.

### 2. Интеграционные тесты (Integration Tests)

Проверяют корректность работы слоя данных (репозиториев) и компонентов со сложной SQL-трансляцией в реальных условиях взаимодействия с СУБД.

* Тесты используют библиотеку Testcontainers для автоматического разворачивания полноценной изолированной базы данных в контейнере `postgres:16-alpine`.

* Перед стартом интеграционных тестов Testcontainers поднимает один чистый контейнер на все тестовые классы, накатывает на него все актуальные миграции EF Core, а после завершения тестов полностью уничтожает окружение. Чтобы тесты не влияли друг на друга и оставались детерминированными, перед выполнением каждого отдельного тест-кейса таблицы полностью очищаются с помощью команды `TRUNCATE ... RESTART IDENTITY CASCADE` (реализовано в методе ResetDatabaseAsync). Это гарантирует, что каждый тест запускается на абсолютно чистой базе данных.

### Запуск всех тестов (в папке EventsRestApi):

⚠️ **Важно:** Для успешного выполнения интеграционных тестов должен быть запущен Docker-демон.

  ```bash
  dotnet test
  ```
