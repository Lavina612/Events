# Event Management API

Распределённая событийно-ориентированная система для управления мероприятиями и системой их бронирования на платформе ASP.NET Core Web API с использованием **.NET 10**, **Apache Kafka** и **PostgreSQL**.
Сервис находится на девятом этапе разработки.

## 🚀 О проекте
Данное приложение представляет собой базовый REST API, реализующий полный цикл CRUD-операций для управления событиями, а также дополнительный функционал для создания бронирования событий и авторизации в системе. 
* **Архитектура**: Микросервисная архитектура с использованием принципов Clean Architecture.  Система разделена на 3 независимых функциональных сервиса (EventService, BookingService и UserService) с использованием паттерна Database-per-Service. Взаимодействие между ними выстроено асинхронно через брокер сообщений Kafka. 
* **Хранение данных**: Полноценная реляционная база данных PostgreSQL для каждого сервиса. Взаимодействие с БД осуществляется через Entity Framework Core. Все сущности сопоставлены с таблицами, а правила валидации данных, связи и ограничения гибко настроены с помощью Fluent API в классах конфигураций. Схема данных полностью управляется миграциями EF Core. При старте приложения миграции применяются автоматически.
* **Валидация**: Автоматическая валидация входных данных на уровне модели DTO с использованием встроенных атрибутов и интерфейса `IValidatableObject`.
* **Фоновая обработка**: Асинхронная обработка заявок на бронирование с использованием встроенных фоновых служб (`BackgroundService`) подтверждает или отклоняет бронирование.

## 🛠️ Требования и настройка окружения
* **.NET 10 SDK** (или новее).
* **СУБД PostgreSQL** (рекомендуется запуск через Docker-контейнер с помощью `docker-compose.yml`).
* **Среда контейнеризации Docker** (Docker Desktop, Rancher Desktop или Colima) — необходима для развёртывания инфраструктуры и выполнения интеграционных тестов.
* **Брокер сообщений Apache Kafka** — используется для асинхронного обмена событиями между сервисами (автоматически разворачивается через `docker-compose.yml`).
* **Настроенные строки подключения и параметры Kafka** в файлах конфигурации `appsettings.json` (или `appsettings.Development.json`) каждого микросервиса.

| Микросервис | Назначение | База данных (PostgreSQL) | Локальный порт (Host) | Порт в Docker (Production) |
| :--- | :--- | :--- | :--- | :--- |
| **UserService** | Управление пользователями, аутентификация и профили. | `eventapi_users` (Port: `5436`) | `localhost:5001` | `user-service:8080` |
| **EventService** | Управление мероприятиями. | `eventapi_events` (Port: `5434`) | `localhost:5002` | `event-service:8080` |
| **BookingService** | Управление бронированиями на мероприятия. | `eventapi_bookings` (Port: `5435`) | `localhost:5003` | `booking-service:8080` |

**Согласно принципу Clean Architecture каждый микросервис внутри построен из изолированных слоев:**
  * `Domain` — ядро приложения. Содержит бизнес-сущности (`Models`), доменную логику и кастомные исключения доменного уровня. Зависит только от общеиспользуемых моделей (`SharedContracts`).
  * `Application` — слой бизнес-логики. Реализует основные сценарии использования системы посредством сервисов (`Services`), содержит контракты репозиториев (`RepositoryInterfaces`), объекты передачи данных (`Dto`), мапперы для преобразования доменных сущностей в DTO и обратно (`Mappers`), классы конфигурации (`Settings`), кастомные исключения прикладного уровня (`Exceptions`) и методы-расширения для централизованной регистрации всех сервисов и компонентов прикладного слоя в DI-контейнере (`Extensions`).
  * `Infrastructure` — слой реализации инфраструктуры. Отвечает за доступ к данным (Entity Framework Core `DbContext`, конфигурации Fluent API, `Repositories`), управление миграциями базы данных и регистрацию внешних зависимостей, таких например как `MessageBroker`, а также содержит методы-расширения для централизованной регистрации всех внешних зависимостей инфраструктурного слоя в DI-контейнере (`Extensions`).
  * `Presentation` — точка входа и слой представления (ASP.NET Core Web API). Содержит контроллеры (`Controllers`), кастомные `Middlewares` для глобальной обработки ошибок, файлы конфигурации (`appsettings.json`, `appsettings.Production.json`) и класс `Program.cs`.
  * **Общая библиотека контрактов (`src/Shared/EventsRestApi.Services.SharedContracts`)**: Вынесена в независимый проект. Содержит разделяемые DTO, записи событий Kafka (`BookingConfirmedEvent`, `BookingCancelledEvent`) и константы топиков (`BookingTopics`), изолируя сетевые контракты от доменных моделей.

## 📦 Миграции базы данных (EF Core)

Каждая база данных инициализируется и обновляется с помощью механизма миграций Entity Framework Core. При запуске приложения миграции применяются автоматически, разворачивая актуальную схему.

### 🗺️ Управление миграциями

При внесении изменений в модели данных или конфигурации Fluent API, необходимо обновить миграции.

Для управления миграциями, находясь в корневой папке решения (`EventsRestApi`), используйте следующие команды:

* **Установка утилиты `dotnet ef` (если ещё не установлена):**
  ```bash
  dotnet tool install --global dotnet-ef
  ```

* **Создание новой миграции:**
  ```bash
  // Создание миграции для BookingService 
  dotnet ef migrations add <Название_Миграции> --context BookingDbContext --project .\EventsRestApi.Services.BookingService.Infrastructure --startup-project .\EventsRestApi.Services.BookingService.Presentation

  // Создание миграции для EventService
  dotnet ef migrations add <Название_Миграции> --context EventDbContext --project .\EventsRestApi.Services.EventService.Infrastructure --startup-project .\EventsRestApi.Services.EventService.Presentation

  // Создание миграции для UserService
  dotnet ef migrations add <Название_Миграции> --context UserDbContext --project .\EventsRestApi.Services.UserService.Infrastructure --startup-project .\EventsRestApi.Services.UserService.Presentation
  ```
  
* **Ручное применение миграций на локальную БД:**
  ```bash
  // Применение миграции для BookingService
  dotnet ef database update --context BookingDbContext --project .\EventsRestApi.Services.BookingService.Infrastructure --startup-project .\EventsRestApi.Services.BookingService.Presentation

  // Применение миграции для EventService
  dotnet ef database update --context EventDbContext --project .\EventsRestApi.Services.EventService.Infrastructure --startup-project .\EventsRestApi.Services.EventService.Presentation

  // Применение миграции для UserService
  dotnet ef database update --context UserDbContext --project .\EventsRestApi.Services.UserService.Infrastructure --startup-project .\EventsRestApi.Services.UserService.Presentation
  ```
  
* **Удаление последней (еще не примененной) миграции:**
  ```bash
  // Удаление последней миграции для BookingService
  dotnet ef migrations remove --context BookingDbContext --project .\EventsRestApi.Services.BookingService.Infrastructure --startup-project .\EventsRestApi.Services.BookingService.Presentation

  // Удаление последней миграции для EventService
  dotnet ef migrations remove --context EventDbContext --project .\EventsRestApi.Services.EventService.Infrastructure --startup-project .\EventsRestApi.Services.EventService.Presentation

  // Удаление последней миграции для UserService
  dotnet ef migrations remove --context UserDbContext --project .\EventsRestApi.Services.UserService.Infrastructure --startup-project .\EventsRestApi.Services.UserService.Presentation
  ```

### 📊 Миграции в проекте

Схемы используют стратегию именования `snake_case` (все таблицы, колонки и ограничения пишутся строчными буквами через подчеркивание).

#### 1. EventService: InitialEventDb

Миграция создает таблицу `events` в соответствии с конфигурациями Fluent API с встроенными проверками данных на уровне СУБД:

**Таблица `events` (Мероприятия)**
* `id` (`uuid`, Primary Key) — уникальный идентификатор мероприятия (генерируется на стороне приложения).
* `title` (`varchar(250)`, Not Null) — название мероприятия с ограничением до 250 символов.
* `description` (`varchar(2000)`, Nullable) — описание мероприятия с ограничением до 2000 символов.
* `start_at` (`timestamp with time zone`, Not Null) — дата и время начала  мероприятия (связано с приватным полем `_startAt`).
* `end_at` (`timestamp with time zone`, Not Null) — дата и время окончания мероприятия (связано с приватным полем `_endAt`).
* `total_seats` (`integer`, Not Null) — общее количество мест на мероприятии (связано с приватным полем `_totalSeats`).
* `available_seats` (`integer`, Not Null) — количество оставшихся свободных мест (связано с приватным полем `_availableSeats`).

**🔒 Проверки целостности (Check Constraints):**
* `CK_Event_Dates`: Дата начала должна быть строго меньше даты окончания (`start_at < end_at`).
* `CK_Event_TotalSeats`: Общее количество мест должно быть положительным числом (`total_seats > 0`).
* `CK_Event_AvailableSeats`: Количество свободных мест не может быть отрицательным и не может превышать общее количество мест на мероприятии (`available_seats >= 0 AND available_seats <= total_seats`).

#### 2. BookingService: InitialBookingDb

Миграция создает таблицу `bookings` в соответствии с конфигурациями Fluent API с встроенными проверками данных на уровне СУБД:

**Таблица `bookings` (Бронирования)**
* `id` (`uuid`, Primary Key) — уникальный идентификатор брони (генерируется на стороне приложения).
* `event_id` (`uuid`, Not Null) — уникальный идентификатор события, связывающий бронирование с мероприятием.
* `user_id` (`uuid`, Not Null) — уникальный идентификатор пользователя, связывающий бронирование с создавшим его пользователем.
* `status` (`varchar`, Not Null) — текущий статус обработки, сохраняемый в виде строки (`Pending`, `Confirmed`, `Rejected`).
* `booked_seats` (`integer`, Not Null) — количество забронированных мест.
* `created_at` (`timestamp with time zone`, Not Null) — дата и время создания заявки.
* `processed_at` (`timestamp with time zone`, Nullable) — дата и время обработки заявки фоновым сервисом.

**🔒 Проверки целостности (Check Constraints):**
* `CK_Booking_BookedSeats`: Количество бронируемых мест должно быть больше нуля (`booked_seats > 0`).
* `CK_Booking_Dates`: Заявка не может быть обработана раньше, чем она была создана (`processed_at IS NULL OR created_at <= processed_at`).

#### 3. UserService: InitialUserDb

Миграция создает таблицу `users` в соответствии с конфигурациями Fluent API с встроенными проверками данных на уровне СУБД:

**Таблица `users` (Пользователи**
* `id` (`uuid`, Primary Key) — уникальный идентификатор пользователя.
* `login` (`text`, Not Null) — логин пользователя для авторизации.
* `hashed_password` (`text`, Not Null) — хэшированный пароль.
* `role` (`text`, Not Null) — роль пользователя в системе.

**⚡ Индексы:**
* `ix_users_login`: Уникальный индекс (`unique: true`) на колонку `login` для предотвращения регистрации дубликатов.

## 📐 Архитектурные и технические решения

### 📖 Документация API и Swagger

Для каждого микросервиса доступна интерактивная документация Swagger UI (ссылка + `/swagger`).

### 🔒 Аутентификация и Авторизация

В проекте реализована полноценная система аутентификации и авторизации пользователей на основе **JWT (JSON Web Tokens)** и хэширования паролей с помощью алгоритма SHA-256.

#### 🛠️ Настройка конфигурации (appsettings.json)

Для корректной работы системы авторизации и запуска приложения необходимо заполнить секцию `JwtSettings` в файле конфигурации `appsettings.json`.

Пример структуры файла:

```json
{
  "JwtSettings": {
    "Issuer": "EventsRestApi.Backend",
    "Audience": "EventsRestApi.Clients",
    "Secret": "Здесь_должна_быть_ваша_длинная_секретная_строка_минимум_256_бит",
    "LifetimeInMinutes": 60
  }
}
```

> ⚠️ **Важно:** Секретный ключ (`Secret`) должен быть достаточно длинным для обеспечения безопасности подписи алгоритма HMAC-SHA256. В реальных production-средах никогда не храните реальные секреты в `appsettings.json`, используйте Environment Variables или секрет-менеджеры (например, User Secrets для локальной разработки).

#### 🎫 Механизм работы JWT

1. **Генерация токена:** При успешном вызове `/user/login` сервис генерирует токен, в который зашиваются утверждения (Claims) о пользователе:
   * Идентификатор пользователя (`nameid` / `NameIdentifier`)
   * Логин (`unique_name` / `Name`)
   * Роль (`role` / `Role`), определяющая уровень прав доступа к эндпоинтам (например, `Admin`, `User`).
2. **Валидация:** При получении запроса API строго сверяет издателя (`Issuer`), аудиторию (`Audience`), проверяет срок действия токена (`Lifetime`) с учетом нулевого временного сдвига (`ClockSkew = TimeSpan.Zero`), а также контролирует валидность подписи ключа (`Secret`).

#### 👥 Ролевая модель (Матрица доступа)
Доступ к эндпоинтам системы разграничен на три уровня в зависимости от статуса аутентификации и роли пользователя:

* **🌐 `Гость` (Неавторизованный пользователь):**
  * Может просматривать полный список доступных мероприятий с использованием фильтров и пагинации.
  * Может просматривать информацию о конкретном событии по его идентификатору.
* **🔑 `User` (Авторизованный пользователь):**
  * Обладает всеми возможностями `Гостя`.
  * Может создавать заявки на бронирование мероприятия.
  * Может просматривать список с информацией о всех своих бронированиях.
  * Может отменять свои бронирования.
* **🔐 `Admin` (Администратор):**
  * Обладает всеми возможностями `User`.
  * Может управлять мероприятиями: создание, изменение и удаление события.
  * Может просматривать учетные данные зарегистрированных пользователей по их `id`.
  * Может отменять любые бронирования.

#### 🔑 Хэширование паролей

В целях безопасности пароли пользователей не хранятся в открытом виде. При регистрации пароль переводится в верхний регистр Hex-строки хэша **SHA-256** силами `PasswordService`. Валидация при входе происходит путем сравнения хэша заново введенного пароля с хэшем из базы данных.

### ⚠️ Правила валидации данных (DTO)

При отправке запросов `POST` и `PUT` данные автоматически проверяются по следующим критериям:
1. Название события (`Title`) обязательно для заполнения и не может быть пустым.
2. Даты начала (`StartAt`) и окончания (`EndAt`) мероприятия обязательны для заполнения.
3. Дата окончания мероприятия (`EndAt`) должна быть позже даты начала (`StartAt`).
4. Общее количество мест на мероприятии (`TotalSeats`) обязательно для заполнения и должно быть положительным числом.

#### Пример данных в формате JSON, которые должны быть переданы в теле запроса для создания мероприятия (`POST /events`):
```json
{
  "title": "Мероприятие 1",
  "description": "Описание 1",
  "startAt": "2026-05-10T10:00:00Z",
  "endAt": "2026-05-15T12:00:00Z",
  "totalSeats": 10
}
```
*(Обратите внимание: `id` при создании передавать не нужно, сервер сгенерирует его автоматически)*.

#### Пример данных в формате JSON, которые должны быть переданы в теле запроса при обновлении мероприятия (`PUT /events/{id}`):
```json
{
  "title": "Мероприятие 1",
  "description": "Описание 1",
  "startAt": "2026-05-10T10:00:00Z",
  "endAt": "2026-05-15T12:00:00Z",
  "totalSeats": 10
}
```

### 🛑 Формат ответа при ошибках

В проекте настроена стандартизированная обработка ошибок через глобальный Middleware (`GlobalExceptionHandlingMiddleware`). При возникновении непредвиденных исключений сервер возвращает ответ в общепринятом формате **Problem Details** (согласно спецификации RFC 7807):

#### 1. Некорректный запрос (400 Bad Request)
* Нарушение правил валидации DTO.
* Передача некорректных параметров (`ArgumentException` + `paramName`).
* Попытка взаимодействия с уже завершившимся мероприятием (`FinishedEventException` + `eventId`, `endAt`).
* Попытка создать бронирование на мероприятие, которое уже началось (`StartedEventException` + `eventId`, `startAt`).

#### 2. Ошибки аутентификации (401 Unauthorized)
* Неверный логин или пароль при авторизации (`InvalidCredentialsException`).
* Некорректный, просроченный или поврежденный JWT-токен (`InvalidTokenException` + `claimName`).

#### 3. Ошибка авторизации (403 Forbidden)
* У пользователя недостаточно прав для выполнения данной операции (`ForbiddenException` + `userId`).

#### 4. Ресурс не найден (404 Not Found)
* Запрашиваемый ресурс (мероприятие, бронирование или пользователь) не найден в системе (`BaseNotFoundException` + `Id, `resourceType`).

#### 5. Конфликты бизнес-логики (409 Conflict)
* На мероприятии не осталось достаточного количества свободных мест (`NoAvailableSeatsException` + `eventId`, `requestedSeats`, `availableSeats`).
* Пользователь превысил допустимый лимит активных бронирований (`ExceedingActiveBookingLimitException` + `userId`, `bookingLimit`).
* Попытка регистрации пользователя с логином, который уже занят (`UserAlreadyExistsException` + `login`).

#### 6. Внутренняя ошибка сервера (500 Internal Server Error)
* Возвращается при любых непредвиденных технических сбоях в коде приложения. Ошибка логируется на сервере для последующего анализа разработчиками, а клиент получает безопасное стандартизированное сообщение без деталей реализации.

### 🔄 Потоки обмена данными (Message Broker Data Flow)

Взаимодействие между микросервисами изолировано от прямых синхронных HTTP-вызовов и построено на базе асинхронного событийно-ориентированного обмена сообщениями через Apache Kafka. 

Для обеспечения надежности доставки данных (At-Least-Once Delivery) продюсеры используют конфигурацию `Acks = All` и встроенную идемпотентность (`EnableIdempotence = true`), а потребители фиксируют смещения вручную (`EnableAutoCommit = false`) строго после успешной фиксации изменений в базе данных.

При старте фоновая hosted-служба `KafkaInitializerHost` веб-приложения  микросервиса Event самостоятельно проверит доступность брокера `localhost:9092` и автоматически создаст системные топики обмена сообщениями (`booking-confirmed`, `booking-cancelled`), если они ещё не были инициализированы.

---

#### 1. Поток подтверждения бронирования (BookingConfirmed)

Событие сигнализирует о том, что система зафиксировала намерение пользователя занять места, и инициирует асинхронный процесс резервирования ресурсов в сервисе мероприятий.

**🏗 Структура контракта (BookingConfirmedEvent)**
Передается в топик `booking-confirmed` в формате JSON. В качестве Kafka Message Key используется строковое представление `EventId` (для сохранения порядка сообщений по конкретному мероприятию в рамках одной партиции). Пример:
```json
{
  "BookingId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "EventId": "7b124a91-1823-4cbb-92d1-123456789abc",
  "UserId": "0a123b45-6789-4def-aabc-112233445566",
  "BookedSeats": 2,
  "ConfirmedAt": "2026-10-27T17:45:00Z"
}
```

**🔄 Пошаговый жизненный цикл данных:**
1. **Инициация:** Пользователь отправляет HTTP-запрос на создание брони. `BookingService` мгновенно сохраняет запись в БД `eventapi_bookings` со статусом `Pending` и возвращает клиенту статус `202 Accepted`.
2. **Публикация:** Внутренний фоновый воркер `BookingBackgroundService` раз в несколько секунд вычитывает пачку `Pending`-заявок (размер пачки настраивается в конфигурации приложения), переводит их статус в `Confirmed` и вызывает компонент `KafkaEventPublisher`. Событие сериализуется и отправляется в топик `booking-confirmed`.
3. **Потребление:** Фоновый триггер `KafkaBookingEventConsumer` на стороне `EventService` асинхронно перехватывает сообщение из топика.
4. **Бизнес-логика и консистентность:** 
   * Выполняются доменные валидации (проверка существования, контроль того, что событие еще не началось и не завершилось).
   * Происходит бронирование мест на мероприятие путём уменьшения числа `available_seats`.
   * Контекст БД сохраняется (`SaveContextAsync`), и только после этого консьюмер вызывает метод `consumer.Commit(consumeResult)`, подтверждая успешную обработку сообщения в Kafka.

---

#### 2. Поток отмены бронирования (BookingCancelled)

Событие гарантирует, что при отмене бронирования забронированные места будут возвращены в пул доступных мест для других пользователей.

**🏗 Структура контракта (BookingCancelledEvent)**
Передается в топик `booking-cancelled` в формате JSON:
```json
{
  "BookingId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "EventId": "7b124a91-1823-4cbb-92d1-123456789abc",
  "UserId": "0a123b45-6789-4def-aabc-112233445566",
  "BookedSeats": 2,
  "CancelledAt": "2026-10-27T18:00:00Z"
}
```

**🔄 Пошаговый жизненный цикл данных:**
1. **Инициация:** Пользователь или администратор инициирует отмену брони через API `BookingService`. Статус записи в БД `eventapi_bookings` меняется на архивный/отмененный.
2. **Публикация:** `BookingService` незамедлительно генерирует объект `BookingCancelledEvent` и отправляет его в Kafka-топик `booking-cancelled` с ключом `EventId`.
3. **Потребление:** Служба `KafkaBookingEventConsumer` в `EventService` (подписанная параллельно на оба топика в рамках одного бесконечного цикла обработки `StartConsumerLoop`) считывает событие отмены.
4. **Бизнес-логика и консистентность:**
   * Выполняются доменные валидации (существование события).
   * Если событие существует, места освобождаются путём увеличения `available_seats`. 
   * Новое состояние фиксируется в Postgres транзакционным методом `SaveContextAsync`. Кафка получает подтверждение смещения (offset commit).

> ⚠️ **Техническая изоляция отказов:** Если в процессе обработки любого из событий база данных `EventService` временно недоступна или произошел технический сбой, метод обработки возвращает `false`, смещение сообщения в Kafka не коммитится, цикл засыпает на 2 секунды, после чего повторно пытается обработать то же самое сообщение, реализуя паттерн гарантированной доставки данных.

### ⚡️ Кэширование данных (Redis StackExchange)

В микросервис `EventService` интегрировано кэширование на базе **Redis** для снижения нагрузки на реляционную базу данных (PostgreSQL) и ускорения ответов на самые частые запросы чтения.

* **Мягкая деградация (Graceful Degradation):** Сервис спроектирован отказоустойчивым. Любые сетевые сбои, таймауты или недоступность контейнера Redis перехватываются, логируются и не приводят к падению приложения. В случае аварии Redis кэш прозрачно отключается, а запросы временно идут напрямую в PostgreSQL.

---

#### 📈 Сценарии кэширования

В микросервисе реализован классический паттерн Cache-Aside для двух ключевых сценариев, выбрав для каждого оптимальную стратегию инвалидации данных:

**1. Получение события по идентификатору (GET /events/{id})**
* **Ключ в Redis:** `event:{id}`
* **Стратегия инвалидации:** Инвалидация при записи (Cache Eviction) + фиксированный TTL (5 минут).
* **Обоснование:** Актуальность мероприятия критична. При изменении или удалении события мы сначала фиксируем изменения в PostgreSQL, а затем удаляем соответствующий ключ из Redis. Если шаг с кэшем оборвется, данные гарантированно обновятся по TTL. Порядок «сначала база, потом кэш» гарантирует консистентность первоисточника истины.

**2. Топ-10 самых популярных событий (`GET /events/top`)**
* **Ключ в Redis:** `events:top10`
* **Стратегия инвалидации:** Обновление строго по TTL (10 минут).
* **Обоснование:** Данный эндпоинт возвращает рейтинговый агрегат (события с наибольшим процентом проданных мест), расчет которого требует тяжелой сортировки на стороне СУБД. Небольшое устаревание (до 10 минут) здесь некритично для пользователя, поэтому явная инвалидация при каждом бронировании билета была бы избыточной.

## 🧪 Запуск автоматических тестов (xUnit)

В репозитории реализовано два типа автоматических тестов:

### 1. Юнит-тесты (Unit Tests)
Проверяют изолированную бизнес-логику: правильность работы CRUD-операций в сервисе событий, а также сценарии создания бронирований, их получения, и изменения статуса. 

* Для обеспечения скорости выполнения тестов реальная база данных в них не используется — вместо этого в тестовых классах регистрируется провайдер InMemory базы данных (`options.UseInMemoryDatabase`), генерирующий уникальную чистую БД для каждого тестового прогона.

### 2. Интеграционные тесты (Integration Tests)

Проверяют корректность работы слоя данных (репозиториев) и компонентов со сложной SQL-трансляцией в реальных условиях взаимодействия с СУБД.

* Тесты используют библиотеку Testcontainers для автоматического разворачивания полноценной изолированной базы данных в контейнере `postgres:16`.

* Перед стартом интеграционных тестов Testcontainers поднимает один чистый контейнер на все тестовые классы, накатывает на него все актуальные миграции EF Core, а после завершения тестов полностью уничтожает окружение. Чтобы тесты не влияли друг на друга и оставались детерминированными, перед выполнением каждого отдельного тест-кейса таблицы полностью очищаются с помощью команды `TRUNCATE ... RESTART IDENTITY CASCADE` (реализовано в методе ResetDatabaseAsync). Это гарантирует, что каждый тест запускается на абсолютно чистой базе данных.

### Запуск тестов (в папке EventsRestApi):

Находясь в корне репозитория для запуска тестов каждого отдельного микросервиса нужно выполнить следующие команды:

  ```bash
  cd src/Services/<НазваниеСервиса>
  dotnet test
  ```

⚠️ **Важно:** Для успешного выполнения интеграционных тестов должен быть запущен Docker-демон.
